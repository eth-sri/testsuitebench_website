TestSuiteBench:

Can Coding Agents Generate Strong Test Suites from Specifications?

1SRI Lab @ ETH Zurich   2LogicStar.ai

TL;DR

Code generation benchmarks now ask agents to build whole applications, but test generation benchmarks still stop at single functions or bug fixes. TestSuiteBench asks coding agents to write a complete test suite for a real application from its specification alone. It contains 165 open-source applications, each with a detailed specification, a reference implementation, a reference test suite, and requirement-targeted mutants.

What is the task?

Each instance is a real open-source command-line application written in Rust, Go, or C/C++. The agent receives only a natural-language specification of the application's behavior and must write a complete test suite for it from scratch. The reference implementation, the reference tests, and the mutants stay hidden. Agents run in a Docker container without internet access.

  • 165applications
  • 5.6kwords per specification
  • 679reference tests per app
  • 67mutants per app

What do you measure?

Mutation score ℳ
The fraction of mutants killed by the generated test suite; this is the main metric. Only tests that pass on the reference executable count, so a test that fails everywhere cannot inflate the score. The reference suite kills every mutant, so 100% is attainable.
Validity 𝒱
The fraction of generated tests that pass on the reference executable. Flaky tests are removed.
Reference pass rate ℛ
For comparison, the same agent also implements the application from the same specification. ℛ is the fraction of reference tests that this implementation passes.

Findings

  • Agents write weak test suites. The best agent kills only 55.5% of mutants, and four of six agents stay below 40%.
  • The tests are valid, just not strong. 88% of generated tests pass on the reference implementation, and implementations the same agents build from the same specifications pass up to 93% of the reference tests.
  • Model-generated test suites are small. Generated suites are smaller than the reference suites and miss the input combinations needed to expose broken requirements.

How is the benchmark built?

  1. Implementation I and tests T. We start from the reference implementations and test suites of ProgramBench and filter out flaky and resource-heavy tests.
  2. Draft specification S′. A coding agent writes a specification describing every behavior tested by T.
  3. Mutants M. For each specification section, a coding agent modifies I to break one requirement. We refine the mutants so that 73% are killed by exactly one test in T (up from 32%).
  4. Final specification S. Agents generate implementations and tests from S′. We fix every failure caused by an ambiguous or contradictory specification and repeat until fewer than 5% spec-related errors are detected. A final manual check follows, giving S.
